# Architecture

## System shape

The app is a single Android application module (`:app`) using Kotlin, Jetpack Compose, Room, SQLCipher, WorkManager and DataStore. It follows an explicit layered package structure rather than a framework-heavy architecture.

### UI layer

`app/src/main/java/ir/restaurant/management/ui`

Compose screens, navigation-facing state and UI interactions. Business/financial writes must not originate as raw SQL or journal inserts from UI code.

### Domain layer

`app/src/main/java/ir/restaurant/management/domain`

Domain models, repository/service interfaces, security permissions and business contracts grouped by areas such as accounting, inventory, procurement, personnel, payroll, sales, receivables, control, recipe and treasury.

### Application layer

`app/src/main/java/ir/restaurant/management/application`

Use-case orchestration for bounded application actions where present.

### Data layer

`app/src/main/java/ir/restaurant/management/data`

Room database/DAOs/entities/migrations, repository implementations, security key management, sync transport, backup validation and treasury implementations.

### Dependency composition

`AppContainer` performs manual dependency composition. This avoids an additional DI dependency but currently creates a large composition root. It is an architectural boundary, not a place for business rules.

## Database

- Database class: `data/db/AppDatabase.kt`
- Current schema constant: `APP_DATABASE_SCHEMA_VERSION = 54`
- Room export: enabled to `app/schemas`
- Encryption: SQLCipher `SupportOpenHelperFactory`
- Migration registry: `data/db/migration/AppMigrations.kt`
- Current final migration: `MIGRATION_53_54`
- Destructive fallback: forbidden and not part of the intended production database strategy.

Schema 54 export is currently missing from the repository and must be generated by Room in a working build environment. Historical schema files are preserved; no 54.json is fabricated.

## Branch-aware accounting journal

The existing `journal_entries` table remains the canonical accounting header. Schema 53 introduced structural `branchId` plus explicit `accountingScope` (`BRANCH`, `ORGANIZATION`, `UNASSIGNED_LEGACY`). Schema 54 appends one canonical `BranchEntity` master and canonical `branchId` columns to the remaining Phase 2 business paths that previously depended on branch strings. No parallel accounting or Branch core is introduced. Branch P&L reads only `BRANCH` journals for the requested numeric branch; organization-wide and unverifiable historical journals stay excluded.

Legacy branch strings are compatibility/display inputs only. Migration 53→54 preserves trusted numeric branch identities first and backfills text only through exact deterministic legacy keys; blank/unknown/ambiguous values remain unassigned instead of falling back to Branch 1.

## Financial integrity boundaries

The project contains explicit accounting, treasury, receivable, daily-sales and inventory-ledger services. New financial flows should preserve:

1. transaction atomicity,
2. idempotency for post/reverse actions,
3. audit events,
4. canonical receivable ledger/master invariants,
5. branch scope,
6. no direct inventory balance mutation outside the ledger/command model,
7. no tax-as-revenue or collection-as-new-revenue semantic drift.

## Security boundaries

- `DatabaseKeyProvider` owns local secret wrapping using Android Keystore.
- SQLCipher owns encrypted database storage.
- `SessionAuthorizer`/authorization services own action permission enforcement.
- `HttpsSyncTransport` and `SyncTokenRefresher` own HTTPS network calls.
- `SyncSafetyGate` currently keeps cloud sync fail-closed for production readiness.

## State and background work

Compose state/ViewModels are used for UI state. WorkManager is present for deferred background work. Sync scheduling is gated by `SyncSafetyGate`.

## Large-file review

The audit identified several high-responsibility files, including `LocalHrPayrollService.kt`, `LocalPersonnelRepository.kt`, `LocalDailySalesRepository.kt`, `OperationsMigrations.kt`, and large UI files. They are maintenance debt candidates. They were **not** split mechanically during this audit because Gradle compilation/tests are blocked; invasive refactoring of payroll/financial code without executable verification would increase risk. Recommended decomposition is documented in `KNOWN_ISSUES.md`.

## Architecture change policy

Refactor only when it improves cohesion/testability or reduces coupling. Do not change business behavior merely to fit a pattern or reduce file length. Every business-rule change must have a focused behavioral test and migration impact assessment where relevant.
