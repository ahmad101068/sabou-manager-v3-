# Standardization Decisions

## D-001 — Room v55 compatibility migration is approved by Phase-3 Gate 0

The approved v54 Business Core remains frozen, but a test-proven Dashboard rename defect requires one compatibility migration: `MIGRATION_54_55`. All historical migrations/tests remain, `54.json` is preserved, and `55.json` is generated by Room/KSP. The migration adds only `branch_legacy_aliases`; it does not rewrite historical financial rows.

## D-002 — Branch identity

Numeric `branchId` is canonical. Fresh-install management is added without creating a synthetic Branch 1. Existing deterministic text resolver code is retained as the v55 upgrade-compatibility adapter for historical data and pre-canonical DTO inputs; it must resolve to one active canonical Branch before branch-scoped persistence.

## D-003 — Referential-integrity gaps do not trigger a schema change here

Where a branch-scoped table does not currently carry a Room foreign key to `branches.id`, this gate does not add one because doing so requires a new schema migration. New write paths validate Branch existence/activity in canonical services. FK hardening is a future schema-change candidate with migration tests.

## D-004 — Dashboard legacy text is resolved through a stable branchId compatibility boundary

`DashboardAnalyticsDao` may read historical textual fields only through deterministic `branch_legacy_aliases` selected by canonical `branchId`. Current display names are not identity. Rename records aliases; ambiguous normalized aliases are excluded from branch-specific attribution rather than matched to multiple branches.

## D-005 — KDF format is not changed without compatibility tests

Credential and portable-backup PBKDF2-HMAC-SHA1 formats are security modernization targets. Existing tests assert current formats, so this gate documents rather than silently changes them.

## D-006 — Canonical documentation

`README.md` is the only metadata source of truth. Historical reports live under `docs/history/` and are excluded from current-documentation gates. `docs/PAYROLL-CALCULATION-SPEC.md` is retained because it is a current business specification.

## D-007 — Phase-3 UI foundation

Phase 3 introduces the five-destination top-level navigation and reusable `ManagementDataGrid`/`MobileSmartRow` foundation before module redesign. Business formulas, posting semantics, and authorization stay outside composables and remain frozen.

## D-008 — Legacy branch text cannot become a second identity

Existing pre-canonical DTOs in Procurement, Personnel, Inventory, Assets, and Payroll may still carry an optional legacy branch text key. `CanonicalBranchResolver` converts that key to exactly one active `BranchEntity`; numeric `branchId` is the only identity used by downstream branch-scoped persistence/posting. New APIs must pass `branchId` directly. Removing the compatibility adapter is deferred because the Room upgrade contract through v55 is preserved and full runtime safety coverage belongs to Phase 3.


## D-009 — Gate-0 bug evidence

- `BUG_EVIDENCE`: Dashboard legacy sales/customer analytics filtered by mutable Branch display text; a rename could detach historical rows from the selected Branch.
- `ROOT_CAUSE`: legacy rows lack numeric `branchId`, while the compatibility boundary converted canonical selection back to the current `branchName`.
- `AFFECTED_DOMAIN`: Dashboard legacy analytics compatibility only.
- `MINIMAL_FIX`: Room v55 `branch_legacy_aliases`, alias capture on create/rename, deterministic unique mapping, no historical financial-row rewrite.
- `REGRESSION_TEST`: `DashboardBranchRenameCompatibilityIntegrationTest`, `Migration54To55Test`, and `FullMigration1ToCurrentTest`.


## D-010 — Phase-3 test debt discovered by real execution

Actual `testDebugUnitTest` execution on both the untouched approved baseline and Part 1 reproduced three baseline failures. Two were test-harness defects only: Long values were compared through JUnit's object overload using Int literals, and two JUnit4 expression-body tests returned the exception object instead of `Unit`; their assertions remain unchanged. The third exposed permission drift: `CASHIER` retained legacy `SALES` but the canonical Daily Sales route requires `DAILY_SALES_VIEW`, so the existing cashier quick-action contract could not be satisfied. The minimal production fix grants `CASHIER` only `DAILY_SALES_VIEW`; no create/edit/confirm/post/void Daily Sales permission is added.
